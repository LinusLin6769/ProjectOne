# AI cost alternatives (T-011)
## Constraints (from the user directly)
- Hardware: MacBook with Apple **M2 Pro**, **16GB unified memory**.
- Usage: AI spend is **mostly agentic coding/orchestration work** (Warp/Oz), not a broad mix of other AI tools.
- Goal stated explicitly: not cost-constrained, not dogmatically anti-paid — wants a real survey of genuinely open/free options, not just a different paid vendor (BYOK to another API is not the ask).
## The core tension
16GB of *unified* memory (shared by macOS, every open app, and the model — not dedicated VRAM) caps what's locally runnable to roughly 7B–8B parameter models comfortably, 14B tight-but-possible with little else running, and nothing near 32B. Meanwhile the workload that's actually costing money is **multi-step agentic orchestration** (planning, multi-file edits, tool use across a whole session) — precisely the capability that drops off fastest as model size shrinks. Autocomplete/single-file/well-scoped tasks hold up fine on small local models; the parallel-worktree, multi-track orchestration this repo does does not. That mismatch is the headline finding below.
## Open-source coding-agent CLIs (model-agnostic, BYOK-or-local)
All of these are free software; you pay only for whatever model you point them at (including $0 for a local model). Names and shapes are stable/well-established projects — the general landscape:
- **Aider** (Apache 2.0, terminal) — the most git-disciplined option: every change is an auto-commit, has a repo-map for large-codebase awareness, and sends noticeably fewer tokens per turn than full-file-rewrite tools. Weakest on full autonomy (it's a pair-programmer, not a fire-and-forget worker) but the cheapest and most reviewable by design. Best fit for well-scoped, single/few-file tasks — exactly the tier that a local 7B model can handle.
- **Cline** (Apache 2.0, VS Code extension) — approval-gated (you click through each file edit/command), broad model support including Ollama/LM Studio for local models. More autonomous than Aider but reads more files per task, which burns more tokens/is slower on a local model.
- **OpenHands** (MIT, Docker sandbox) — the most autonomous open agent (runs end-to-end in a sandbox, opens PRs). Needs Docker, heaviest setup, and its own docs/community benchmarks are explicit that quality drops sharply below ~32B models — a 16GB Mac is not a good fit for this one.
- **Goose** (Apache 2.0, Linux-Foundation/Block-backed) — vendor-neutral, MCP-native, both CLI and desktop app, runs any provider including local. Good "Switzerland" option if MCP-server composability matters more than raw agentic strength.
- **Continue** (Apache 2.0, VS Code/JetBrains) — more autocomplete-and-chat than full autonomous agent; some sources report its main upstream repo has slowed/gone read-only after an acquisition — treat as lower-priority, worth rechecking current maintenance status before investing time.
None of these close the capability gap with Warp/Oz for the kind of parallel, multi-track orchestration this repo relies on — that gap is a function of model capability (frontier vs. small open-weight), not the harness. Swapping the harness alone doesn't buy back the cost; swapping the *model* down to something local is what both saves money and costs capability.
## What's realistically runnable locally on this Mac (M2 Pro, 16GB)
The leading open-weight coding model family is **Qwen2.5-Coder** (Alibaba, Apache 2.0, no usage caps) — it's the model most guides converge on as the best-in-class open coding model per size class, with **DeepSeek-Coder-V2-Lite** (MoE, 16B total/2.4B active) as a solid alternative especially for algorithmic work.
- **Qwen2.5-Coder 7B** (~5GB at Q4 quantization) — the comfortable default on 16GB unified memory. Genuinely strong for single-file generation, bug fixing, explanations, tests, and small refactors. This is the realistic daily-driver size for this hardware.
- **Qwen2.5-Coder 14B** (~9-10GB at Q4) — noticeably stronger on multi-file reasoning, but tight on 16GB once macOS, Warp, a browser, etc. are also resident. Usable, but expect to close other apps or accept slower generation from memory pressure/swapping.
- 32B+ models are out of reach on this hardware (need ~20-24GB just for weights).
**Runtime**: **Ollama** is the pragmatic default — one-command install (`ollama pull qwen2.5-coder:7b`), OpenAI-compatible local API (`localhost:11434`), and every tool above (Aider, Cline, Continue, Goose) already knows how to talk to it. **MLX** (Apple's native framework) is faster on Apple Silicon, but its biggest wins concentrate on 32GB+ Macs — on a 16GB M2 Pro the gap over Ollama's default Metal backend is smaller and the extra Python/setup friction is less worth it. Not worth the switch here; can revisit if RAM increases later.
## Genuinely free/open infrastructure worth knowing about
- **Warp's client is now open-source (AGPL-3.0)** — the terminal/ADE client itself, not the Oz cloud orchestration layer (which stays proprietary). Doesn't change the token-cost equation directly, but confirms Warp's direction is toward more openness, not less.
- **Warp's BYOK is free for individuals on every plan, including Free** — if you bring your own API key or point Warp at any OpenAI-compatible endpoint, Warp doesn't charge credits for that usage. This is BYOK-to-a-vendor (which isn't what you asked for), but the *same mechanism* is how you'd eventually point Warp directly at a **local** model.
- ~~Warp has explicitly announced a lightweight local-model client harness~~ — **UNVERIFIED, likely incorrect.** The orchestrator checked Warp's official docs directly and found no such announcement; Oz's LLM inference always routes through Warp's backend or a configured cloud provider (BYOK/BYOLLM), never a fully local/offline model. Treat this line as noise from the research pass, not a real roadmap item.
- Nothing else surveyed (Aider/Cline/Goose/etc.) has hidden costs beyond the model you choose — they're all genuinely free software.
## OpenClaw deep-dive
OpenClaw (github.com/openclaw/openclaw, openclaw.ai) is real and substantial: ~388k GitHub stars, active daily development (tens of thousands of commits), a non-profit "OpenClaw Foundation" behind it, and sponsors including OpenAI, NVIDIA, and GitHub. It is a different category of tool than the coding-agent CLIs above — not a coding assistant first, but a **self-hosted personal-assistant gateway**: one always-on process (the "Gateway") that bridges messaging channels (WhatsApp, Telegram, Slack, Discord, Signal, iMessage, Matrix, 20+ more) to an LLM-driven agent with real tool access (bash, file read/write/edit, browser, cron, webhooks), plus companion apps for macOS/iOS/Android.
### Architecture, in practice
- **Gateway**: a single Node.js process (`openclaw gateway`) that owns sessions, channel connections, auth, and a WebSocket + HTTP control plane (default port 18789). It's the single point of failure and the single point of control — everything (CLI, web Control UI, macOS app, mobile nodes) is a client of this one process.
- **Agent runtime**: a standard read-context → call-model → run-tool-calls → repeat loop, with context compaction, semantic memory search over Markdown files (`MEMORY.md`, daily notes), and the ability to spawn isolated **sub-agents** for parallel background work — conceptually similar to this repo's worktree-per-track pattern, but subagents inherit whatever model the Gateway is configured with, so parallelism doesn't buy back model capability.
- **Model providers**: genuinely provider-agnostic — 30+ backends via a plugin registry, including OAuth-based subscription reuse (e.g. reusing an existing Claude Pro/Max login via `claude -p`, a "sanctioned integration path" per its docs), API keys, and first-class **local model support**: Ollama (native `/api/chat`, not the OpenAI-compat endpoint, for reliable tool-calling), vLLM (OpenAI-compatible `/v1`, with documented workarounds for Qwen tool-call quirks), llama.cpp (OpenClaw can manage/launch a local `llama-server` itself), and LM Studio.
### Setup effort on this Mac (M2 Pro, 16GB)
Genuinely low for a basic install: `npm install -g openclaw && openclaw onboard --install-daemon` (needs Node 22+, 24 recommended) walks through model auth and installs the Gateway as a `launchd` background service in a few minutes. Connecting one channel (Telegram is the fastest) adds a few more minutes. The Gateway process itself is lightweight (it's just Node.js); it does not need to run inference locally at all if you point it at a cloud/subscription model — the 16GB constraint only bites if you also want the *model* to run locally, in which case the same Qwen2.5-Coder-7B-on-Ollama math from above applies.
### Agentic coding capability vs. Warp/Oz
OpenClaw's bash/read/write/edit tools are real and it can genuinely act as a coding agent — but it is not purpose-built for large-codebase software engineering the way Warp/Oz, Aider, or Cline are: no repo-map/codebase-indexing equivalent, no diff-preview-before-apply UI, no PR-review workflow. It's better understood as a general-purpose "always-on Jarvis with shell access" that *can* write code on request than as an IDE-grade coding-agent replacement. For this repo's parallel multi-track orchestration work specifically, it doesn't close the gap Warp/Oz fills.
### Could it replace T-010 (Slack + scheduled checks) without Oz?
Yes, plausibly, and this is OpenClaw's actual sweet spot: it has native Slack channel support, a built-in cron/webhook system ("automation capabilities" in its docs), and a proactive "heartbeat" polling mode — i.e. the exact shape of T-010's flight-price-monitor-plus-Slack-notification use case, running entirely self-hosted (on this Mac, or a cheap always-on VPS/Raspberry Pi) instead of an Oz Scheduled Agent consuming Warp credits. This is a genuine, concrete alternative worth evaluating for T-010 specifically — see `context/task-launch-infra.md` for the current Oz-based plan this would compete with.
### Rough edges and security caveats (the project is explicit about these)
- **Tools run with full host access by default** for your main session — "the agent has full access when it is just you." Sandboxing (Docker/SSH/OpenShell backends) exists but is opt-in, not default.
- **Inbound messages are untrusted input.** DM-capable channels pair unknown senders by default (a pairing code, not instant access), but the docs are blunt: treat every inbound message as a potential prompt-injection vector, since a message can reach a tool-executing agent. Official guidance explicitly says never run open-to-the-world on a personal Mac, use allowlists, and disable the default 30-minute heartbeat polling until you trust the setup.
- **This changes the model-choice calculus.** OpenClaw's own docs recommend "the strongest latest-generation model available" specifically for *security*, not just quality — a weak/small local model is more exploitable by adversarial-looking inbound channel messages, not merely lower-quality. That's in tension with pairing this with the cheapest local 7B model: for anything Slack/Telegram-facing, a more capable (likely still-paid, or at least a stronger free-tier) model is the safer choice, which caps how much of this can be truly $0.
- **License is muddled.** Docs describe it as "MIT licensed," but GitHub's own license detector flags the repo as `Other` rather than a recognized OSI license — worth reading the actual `LICENSE` file before relying on it for anything beyond personal use.
- Genuinely free-tier note: the docs mention a **Qwen OAuth device-code flow providing free access to Qwen's Coder + Vision models** as a built-in auth option — a real $0 cloud-model path worth checking if pursuing this further.
## Comparable self-hosted personal-agent-gateway alternatives
Surveying OpenClaw's actual category (self-hosted, model-agnostic, action-taking personal agents/gateways) rather than the coding-agent-CLI category covered above:
- **Hermes Agent** (Nous Research) — the closest direct comparable to OpenClaw: same "personal assistant across many chat platforms" shape, with a distinguishing self-improving/learning-loop design and Honcho-based user modeling. Leans on hosted sandbox/hibernation infra (Modal/Daytona) for its execution model, which makes it less purely "just runs on your Mac" than OpenClaw and reintroduces a hosted-infra cost dimension. Worth a look if OpenClaw's plain Gateway model doesn't fit, but OpenClaw is the more self-contained option for this use case.
- **Letta** (successor to MemGPT) — not a ready-to-run assistant; a stateful-agent *framework* focused on explicit persistent-memory blocks. Useful if building a custom agent from scratch matters more than getting something running today; not a like-for-like OpenClaw alternative.
- **LibreChat, Open WebUI, AnythingLLM** — all real, mature, MIT-licensed (Open WebUI's license has a branding-restriction clause above 50 users, not a concern for personal use) self-hosted **chat UIs**, not action-taking personal-assistant gateways. They're front-ends over a model (plus RAG for LibreChat/AnythingLLM's document workspaces), with no native multi-channel messaging, no cron/heartbeat automation, and comparatively limited or no tool-execution-on-your-behalf story. Good if the goal is "a private ChatGPT," wrong category for replacing what Oz/T-010 does.
- **Onyx (formerly Danswer)** — enterprise knowledge-search platform (40+ connectors, permission-aware retrieval, citations). Solves "search across our company's tools," not personal automation/messaging — not comparable to OpenClaw for this use case.
- **Dify, Flowise, n8n** — visual builders/workflow engines where you construct agents/automations yourself; more building-block than ready-made assistant. n8n in particular is fair-code (Sustainable Use License), not OSI open source — fine for personal use, worth noting given the "genuinely open-source" framing of this whole track.
Bottom line on the category survey: **OpenClaw is the standout fit** for what would functionally replace Oz's role in T-010 (and potentially light general-purpose automation elsewhere in ProjectOne) — nothing else surveyed combines self-hosted, multi-channel, cron-native, tool-executing, and model-agnostic in one project as directly.
## Recommendation
**Adopt now (low lift, real $0 upside):** Install Ollama + `qwen2.5-coder:7b`, and use **Aider** against it for well-scoped, single/few-file coding tasks — quick scripts, small feature edits, boilerplate, DIY-panel-style code, test writing, explaining unfamiliar code. This is a ~15-minute setup, costs nothing to run, and Aider's git-native discipline (auto-commit per change) fits this repo's existing git-first culture well. Use it as a *first pass* for simple, mechanical coding work before reaching for a paid agent.
**Worth a real pilot, separately: OpenClaw for T-010.** Instead of building T-010's Slack-notification + scheduled-monitoring plan on Oz Scheduled Agents (which consumes Warp credits and requires a paid Warp team plan per `context/task-launch-infra.md`), self-hosting OpenClaw's Gateway with cron + Slack could deliver the same flight-price-monitor/notification pattern for $0 in platform fees. The tradeoffs to weigh before committing: it's a new piece of always-on infrastructure to operate and secure (not "no ops" the way an Oz Scheduled Agent is), the security posture requires real care (untrusted inbound messages reaching a tool-executing agent), and — per OpenClaw's own guidance — the model behind it shouldn't be the cheapest option given the security stakes, so this isn't a fully $0 swap once a competent model is factored in. Still, it's the single most concrete, actionable finding from this research and worth a scoped trial before the user commits further to the Oz-based plan.
**Don't expect either of the above to move the needle on the actual Warp/Oz coding-orchestration spend.** That spend is driven by multi-track agentic orchestration — parallel worktrees, cross-file reasoning, long planning sessions — which is exactly where small open-weight models (7B, even 14B) fall furthest behind frontier hosted models, and exactly what OpenClaw (general-purpose, not codebase-aware) and the coding CLIs (capable, but ceiling-limited by local model size) don't fully replace. Running OpenHands or Cline locally on this hardware for that class of work would trade real reliability for a cost saving that's probably not worth it given the user's stated goal isn't cost-minimization for its own sake.
**Bigger lift, not recommended right now:** Upgrading to a 32GB+ Mac would unlock 27-32B models (closer to genuinely competitive with hosted models on many coding tasks) and MLX's full speed advantage. That's a hardware purchase decision, not a software one — flagging it as the real ceiling-raiser if local inference becomes more of a priority later, but not something to act on today.
**Realistic shift-off estimate:** Maybe 10-20% of day-to-day coding-adjacent work (the simplest, most mechanical slice) could move to a free local Aider+Ollama setup at effectively no quality cost. Separately, the recurring-monitoring/notification slice of ProjectOne's workload (T-010-shaped work) could plausibly move to a self-hosted OpenClaw setup instead of Oz credits, pending a real security/ops evaluation. The bulk of what drives Warp/Oz spend — the parallel multi-agent coding orchestration this repo is built around — has no genuinely open substitute yet at comparable quality on this hardware. The honest conclusion is: worth doing both free things for their own sake, not worth restructuring the core coding workflow around either.
